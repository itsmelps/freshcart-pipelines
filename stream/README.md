# Part D: Food-order stream with RabbitMQ

## D1. Routing on paper

| Routing key | Receiving driver queues |
|---|---|
| `bangalore.koramangala.food` | Ravi, Meena, Control |
| `bangalore.indiranagar.ride` | Priya, Arjun, Control |
| `bangalore.whitefield.ride` | Arjun, Control |
| `chennai.tnagar.food` | Karthik |
| `chennai.whitefield.ride` | dropped |
| `bangalore.koramangala` | Control |

For `bangalore.koramangala`, `Control`'s `bangalore.#` matches: the literal first word is `bangalore` and `#` can match zero words after it. All other bindings have three words: their fixed words must match exactly, and each `*` must consume exactly one word. Since this key has only two words, none of those bindings can match it.

## D2. Run the stream

Install the requirements and start RabbitMQ locally, or set `AMQP_URL` to a hosted broker URL. Keep hosted credentials out of Git.

```powershell
python -m pip install -r requirements.txt
```

In separate terminals, start the six assignment drivers with their bindings:

```powershell
python stream\driver.py Ravi "bangalore.koramangala.*"
python stream\driver.py Priya "bangalore.indiranagar.*"
python stream\driver.py Arjun "bangalore.*.ride"
python stream\driver.py Meena "bangalore.*.food"
python stream\driver.py Karthik "chennai.tnagar.food"
python stream\driver.py Control "bangalore.#"
python stream\dispatcher.py
```

The dispatcher publishes a random Bangalore or Chennai request every two seconds. It stops with Ctrl+C. `AMQP_URL` defaults to `amqp://guest:guest@localhost:5672/%2F`. Each driver binds an exclusive, auto-delete queue and acknowledges valid messages.

To check a specific D1 route, start the six drivers and run (once) in another terminal:

```powershell
python stream\dispatcher.py --routing-key bangalore.koramangala.food
```

For `bangalore.koramangala.food`, Ravi, Meena, and Control receive the message; no other assignment binding matches it. Repeat with each D1 key to verify the table. The fifth key is dropped, so no driver logs a receipt. Queue names are generated by RabbitMQ and vary per run.

Expected output for that one-shot route check (example only; no broker is available in this environment):

```text
[PUBLISHED] id=1-a1b2c3d4 routing_key=bangalore.koramangala.food payload={"id": "...", "city": "bangalore", "zone": "koramangala", "type": "food", "ts": "..."}
[RECEIVED] driver=Ravi routing_key=bangalore.koramangala.food request=...
[RECEIVED] driver=Meena routing_key=bangalore.koramangala.food request=...
[RECEIVED] driver=Control routing_key=bangalore.koramangala.food request=...
```

## D3. ACK and NACK

The dispatcher omits `zone` from every tenth message. A driver rejects a request without `zone` using `basic_nack(requeue=False)`; requests with the field are processed and acknowledged using `basic_ack`. Invalid JSON is also rejected rather than left unacknowledged.

Run the dispatcher for two minutes with the six drivers above plus a catch-all observer, so every generated message reaches a consumer for the ACK/NACK demonstration:

```powershell
python stream\driver.py Audit "#"
python stream\dispatcher.py
```

The observer receives a copy of every published message; each of the six assignment drivers still gets only its own matching copies. This guarantees that the malformed tenth message is visible as a `[NACK discard]` and ordinary messages as `[RECEIVED]` / `[ACK]`. The routing key is still generated from the selected city, zone, and type, even when the payload's `zone` is omitted.

Expected log shape (example; this is illustrative, not output captured from a broker):

```text
[PUBLISHED] id=1-a1b2c3d4 routing_key=bangalore.koramangala.food payload={"id": "...", "city": "bangalore", "zone": "koramangala", "type": "food", "ts": "..."}
[RECEIVED] driver=Ravi routing_key=bangalore.koramangala.food request={"id": "...", "city": "bangalore", "zone": "koramangala", "type": "food", "ts": "..."}
[ACK] driver=Ravi id=...
[PUBLISHED] id=10-e5f6a7b8 routing_key=bangalore.koramangala.food payload={"id": "...", "city": "bangalore", "type": "food", "ts": "..."}
[NACK discard] driver=Ravi routing_key=bangalore.koramangala.food reason=missing zone payload=...
```

If a driver crashes before acknowledging, RabbitMQ requeues its unacknowledged delivery when that consumer's channel or connection closes, so it can be delivered again (at-least-once delivery). With `requeue=True`, a permanently bad message can be delivered repeatedly, creating a poison-message loop; rejecting it with `requeue=False` discards it (or routes it to a configured dead-letter exchange).
